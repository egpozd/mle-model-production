# Мониторинг
Instrumentator предоставляет http_requests_total и стандартные гистограммы HTTP-задержки. Ответы 422 показывают нарушения схемы; 500 — ошибки вычисления. user_id не используется в метках, чтобы число временных рядов не росло с числом пользователей.

Собственные метрики: real_estate_predictions_total — Counter с результатом success/error; real_estate_prediction_seconds — Histogram времени модели; real_estate_price_rubles — Histogram прогнозов в рублях. Ошибки валидации возникают до модели и учитываются HTTP-метриками.

Панели:
- Интенсивность запросов /predict: временной график показывает рост нагрузки и остановки обращений.
- P95 модели: временной график показывает замедления; это оценка по корзинам, а не точный квантиль.
- Доля ошибок HTTP на /predict: Stat удобен для оценки текущей доли 4xx и 5xx.
- Прогнозы по верхней границе цены: Bar gauge показывает накопленные значения гистограммы. Корзины кумулятивные: каждое значение входит во все подходящие верхние границы, их нельзя суммировать как независимые интервалы.

Без истинных цен можно наблюдать распределение прогнозов, задержки, ошибки и доступность. Сдвиг прогнозов может говорить об изменении входящего потока, но не доказывает ухудшение качества. Для анализа дрейфа входных признаков нужна дополнительная агрегация признаков; сейчас она не реализована. MAE, RMSE и R² доступны после получения фактических цен и сопоставления их с прогнозами; сервис не рассчитывает их в реальном времени.

## Дополнительный инфраструктурный мониторинг

Prometheus формирует метрику `up` для каждой цели сбора. Запрос `up{job="ml_service"}` показывает, удалось ли получить метрики FastAPI: 1 означает успешный сбор, 0 — ошибку. Это проверка доступности `/metrics`, а не качества предсказаний.

В `/metrics` также доступны показатели процесса FastAPI: `process_cpu_seconds_total` (накопленное время CPU) и `process_resident_memory_bytes` (занятая оперативная память). Нагрузку на CPU можно оценивать по скорости изменения счётчика (`rate(process_cpu_seconds_total[5m])`), а рост занятой памяти может указывать на проблемы с её потреблением. Эти метрики относятся к процессу, а не ко всему Docker-контейнеру; доступность стандартных метрик процесса зависит от ОС, здесь они доступны в Linux-контейнере.

Состояние контейнеров и число перезапусков можно проверять через Docker (`docker compose --env-file services/.env ps` и `docker inspect`). Частые перезапуски могут указывать на сбои приложения или нехватку ресурсов. Для сбора CPU и памяти целых контейнеров в Prometheus можно добавить cAdvisor, а для их состояния и перезапусков — подходящий экспортер Docker. Сейчас такие экспортеры в проекте не установлены, отдельных панелей для этих показателей нет.
