# Мониторинг

Instrumentator собирает http_requests_total и стандартные гистограммы времени обработки HTTP-запросов. Ответы 422 указывают на ошибки валидации, а 500 на ошибки вычисления. user_id не используется в метках, чтобы число временных рядов не росло с числом пользователей.

В сервисе есть три собственные метрики. Counter real_estate_predictions_total считает вызовы модели с результатом success/error. Histogram real_estate_prediction_seconds измеряет время работы модели, а Histogram real_estate_price_rubles показывает распределение прогнозов в рублях. Ошибки валидации возникают до вызова модели, поэтому учитываются только в HTTP-метриках.

На дашборде четыре панели:

- Интенсивность запросов /predict. Временной график показывает рост нагрузки и периоды без обращений.
- P95 времени модели. График помогает заметить замедления. P95 оценивается по корзинам гистограммы, поэтому это приближённое значение квантиля.
- Доля ошибок HTTP на /predict. Stat показывает текущую долю ответов 4xx и 5xx.
- Накопленные прогнозы по верхней границе цены. Bar gauge показывает значения корзин гистограммы. Корзины кумулятивные: каждый прогноз учитывается во всех корзинах, верхняя граница которых не ниже его значения. Их нельзя суммировать как независимые интервалы.

Без фактических цен можно следить за распределением прогнозов, задержками, ошибками и доступностью сервиса. Изменение распределения прогнозов может быть связано с изменением входящих данных, но само по себе не доказывает ухудшение качества. Для анализа дрейфа входных признаков нужна дополнительная агрегация, которая сейчас не реализована. Рассчитать MAE, RMSE и R² можно только после получения фактических цен и сопоставления их с прогнозами. Сервис не рассчитывает эти показатели в реальном времени.

## Дополнительный инфраструктурный мониторинг

Prometheus формирует метрику `up` для каждой цели сбора. Запрос `up{job="ml_service"}` показывает, удалось ли получить метрики FastAPI: 1 означает успешный сбор, 0 — ошибку. Это проверка доступности `/metrics`, а не качества предсказаний.

В `/metrics` доступны и показатели процесса FastAPI. Метрика `process_cpu_seconds_total` содержит накопленное время CPU, а `process_resident_memory_bytes` показывает занятую оперативную память. Нагрузку на CPU можно оценить по скорости изменения счётчика (`rate(process_cpu_seconds_total[5m])`). Рост занятой памяти помогает заметить проблемы с её потреблением. Эти показатели относятся к процессу, а не ко всему Docker-контейнеру. Доступность стандартных метрик процесса зависит от ОС; в используемом Linux-контейнере они доступны.

Состояние контейнеров и число перезапусков можно проверять через Docker (`docker compose --env-file services/.env ps` и `docker inspect`). Частые перезапуски могут указывать на сбои приложения или нехватку ресурсов. Для сбора данных о CPU и памяти целых контейнеров можно добавить cAdvisor, а для их состояния и перезапусков — подходящий экспортер Docker. Сейчас эти экспортеры и отдельные панели для таких показателей в проекте отсутствуют.
